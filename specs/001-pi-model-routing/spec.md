# Feature Specification: PI 多厂商模型路由（jev-pi-router）

**Feature Branch**: `001-pi-model-routing`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "PI 执行任务时按任务类型路由模型：强模型（mimo/mimo-v2.6-pro、glm/glm-5.3）写计划、做决策、做 review、做兜底、做主 Agent；flash 模型（deepseek/deepseek-flash、glm/glm-5.3-flash、relay/cmd-deepseek-v4.1-flash、opencode-go/deepseek-flash）实现具体代码。必须解决模型前置缓存问题。核心目标：多厂商融合、多厂商协助相互 review、不绑死厂商。强模型组合后续可配置，提供自动模式/自动探测。主会话逐轮切换仅限 /new 干净会话场景。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 按任务类型自动分档派发（Priority: P1）

开发者在 pi 中发起一个包含设计与实现的编码任务时，系统自动分工：计划、决策、复核、兜底、总控由强模型完成；具体代码编写由成本更低的 flash 档模型以独立执行者的身份完成。开发者不需要手动切换模型，也不用担心任务被全部派给昂贵模型。

**Why this priority**: 这是本功能存在的根本价值——在不损失质量的前提下把编码任务的主消耗从强模型转移到低成本模型，是成本收益的主体来源，可独立交付即产生价值。

**Independent Test**: 用一个真实的"新增一个小功能"任务验收：观察到计划/决策由强模型产出、代码由 flash 档执行者产出、结果经复核后合入，全程无需人工切换模型；对照全程强模型的基线，成本有可统计的下降。

**Acceptance Scenarios**:

1. **Given** pi 会话中强模型池与实现模型池配置就绪，**When** 开发者提出一个包含设计与实现的编码任务，**Then** 计划与决策由强模型产出，代码实现由实现池模型以独立上下文执行者完成，主会话不直接编写代码
2. **Given** 一个纯实现类的子任务（设计已定、改动明确），**When** 路由裁决，**Then** 该子任务派发给实现池模型，不消耗强模型额度
3. **Given** 一个模糊子任务（难以判断属于设计还是实现），**When** 路由裁决，**Then** 由语义决策服务判定类别与复杂度；决策服务不可用时回退默认规则（按设计类处理），任务不中断
4. **Given** 非新建的进行中会话，**When** 任意轮次执行，**Then** 主会话模型保持不变（0 次切换），避免响应延迟劣化

---

### User Story 2 - 多厂商交叉 review（Priority: P2）

开发者希望任务产出不被单一厂商的模型"自我背书"：代码由某厂商模型实现后，必须由不同厂商的强模型复核；计划与架构决策这类高杠杆产物由两个强厂商双向互审，捕获单厂商盲点。

**Why this priority**: 多厂商融合与相互 review 是本功能区别于普通"省钱路由"的核心诉求，直接决定产出可信度；但它建立在 P1 分档派发之上（先有派发，才有复核对象）。

**Independent Test**: 人为让 flash 模型产出一个带隐蔽缺陷的实现，验收复核由异源厂商强模型执行并指出缺陷；再验收一份计划被另一强厂商复核并留下复核意见。

**Acceptance Scenarios**:

1. **Given** 实现池中 A 厂商模型完成代码，**When** 进入 review 环节，**Then** reviewer 是非 A 厂商的强模型，且复核意见被主 Agent 采纳或裁决
2. **Given** 强模型产出的计划或架构决策，**When** 进入 review 环节，**Then** 由另一强厂商复核（双向：A 产 B 审、B 产 A 审），互审结论随产物留痕
3. **Given** 强模型池只有一家可用，**When** 需要互审，**Then** 降级为单厂商 review 并显式标记告警，不静默跳过

---

### User Story 3 - 故障与质量双轨兜底（Priority: P2）

开发者不希望任务因为某个厂商故障或产出质量差而卡死：服务故障时自动换同档厂商重试；产出质量持续不达标时自动升级到强模型重做，全程尽量无需人工干预。

**Why this priority**: 多厂商环境下面单厂商故障是常态而非异常，没有兜底则"不绑死厂商"名不副实；与 P2 review 联动（review 不过触发升级）。

**Independent Test**: 模拟一个厂商超时/配额故障，验收任务在重试预算内自动换厂商完成；模拟一个持续不合格的 flash 产出，验收两轮 review 后自动升级强模型重做。

**Acceptance Scenarios**:

1. **Given** 实现池某厂商超时/配额/限流故障，**When** 派发失败，**Then** 同档换下一个厂商重试，开发者无感知，任务继续
2. **Given** 同一厂商连续多次失败，**When** 达到熔断阈值，**Then** 该厂商被临时停用，冷却期后自动恢复
3. **Given** flash 实现连续两轮 review 不通过，**When** 触发质量升级，**Then** 由强模型（换厂商）重做该部分，原实现被替换
4. **Given** 强模型执行失败，**When** 兜底触发，**Then** 由另一强厂商接管

---

### User Story 4 - 配置化模型池与自动模式（Priority: P3）

维护者可以只改配置就增删厂商、调整强/flash 池与配对规则；也可开启自动模式，由系统按可用性、成本、延迟自动选择强模型组合，不绑死任何厂商。

**Why this priority**: 保证长期可演进与不被单厂商锁定，但不阻塞前三项核心价值的交付。

**Independent Test**: 修改配置把某厂商从实现池移除，验收后续任务不再派发到该厂商（零代码改动）；开启自动模式，验收系统探测并选定了可用的强模型组合。

**Acceptance Scenarios**:

1. **Given** 配置文件中的模型池/配对规则，**When** 维护者增删厂商或调整权重，**Then** 后续任务按新配置路由，无需修改代码
2. **Given** 自动模式开启，**When** 系统启动或池状态变化，**Then** 系统探测各厂商可用性/成本/延迟并自动确定强模型组合，探测失败的厂商被排除
3. **Given** 新会话（/new）且冷缓存，**When** 开发者启用会话内逐轮切换模式（B 模式），**Then** 允许主会话按轮切换模型

---

### Edge Cases

- 实现池全部厂商不可用：故障转移穷尽后升级强模型实现，并在决策日志中标记本次"兜底升级"的成本放大。
- 强模型池全部厂商不可用：任务明确失败并提示维护者，不做静默降级到 flash（避免低质量实现被当作最终产出）。
- 语义决策服务不可用/超时：fail-open 回退默认规则映射，任务不中断；决策缺失记入日志。
- 强模型池只剩一家：互审降级为单厂商 review + 显式告警（见 US2-3）。
- 同一厂商连续失败达到熔断阈值：熔断后若池内剩余厂商不足以继续，触发升级链而不是死循环重试。
- 会话中途需要换模型（如强模型故障接管）：仅允许在执行者/子代理层换，主会话模型不动；极端情况下需换主模型时，向开发者显式提示缓存代价。
- review 意见自相矛盾（reviewer 互相否定）：主 Agent 强模型仲裁，仲裁结论进决策日志。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 维护两个可配置模型池：强模型池（用于计划、决策、review、兜底、主控）与实现模型池（用于具体代码实现）。
- **FR-002**: 系统 MUST 按角色派发：计划/决策/review/兜底/主控 → 强模型池；具体代码实现 → 实现模型池。
- **FR-003**: 具体代码实现 MUST 由独立上下文的执行者（子代理）完成，主会话 MUST NOT 直接编写代码。
- **FR-004**: 非新建会话中主会话 MUST NOT 切换模型（保护响应延迟/前置缓存）；新建（/new）会话 MAY 按轮切换。
- **FR-005**: 路由裁决 MUST 采用混合模式：角色→模型映射走配置表；模糊任务的类别判定、复杂度分级、reviewer 配对由语义决策服务裁决。
- **FR-006**: 语义决策服务不可用或超时时 MUST fail-open 回退默认规则，任务不中断。
- **FR-007**: 代码 review MUST 由与实现者不同厂商的强模型执行。
- **FR-008**: 计划与架构决策 MUST 由两个强厂商双向互审（A 产 B 审、B 产 A 审）。
- **FR-009**: 故障转移 MUST 覆盖超时、配额、限流、服务端错误：同档换厂商重试；同一厂商连续失败 MUST 触发临时熔断，冷却后自动恢复。
- **FR-010**: 质量升级 MUST 覆盖：实现连续两轮 review 不通过 → 升级强模型（换厂商）重做；强模型失败 → 另一强厂商接管。
- **FR-011**: 系统 MUST 记录可审计的路由决策日志：任务分类、模型选择、reviewer 配对、故障转移、质量升级、降级告警，均须留痕。
- **FR-012**: 强模型组合 MUST 支持手动配置，且 MUST 提供自动模式（自动探测可用性/成本/延迟选择强模型组合）。
- **FR-013**: 增删厂商、调整池与配对规则 MUST 仅需修改配置，不修改代码。

### Key Entities *(include if feature involves data)*

- **模型池（强模型池 / 实现模型池）**: 可配置的厂商-模型条目集合；条目含可用性状态、成本/延迟属性、熔断状态。示例条目见 Assumptions。
- **角色**: 主控、计划、决策、review、兜底仲裁、代码实现；每个角色绑定到一个模型池。
- **路由决策记录**: 单次派发的裁决留痕——任务分类结果、所选模型、reviewer 配对、是否 fail-open、是否发生转移/升级。
- **review 配对规则**: reviewer 必须异源（不同厂商）于产出方；计划/决策为强厂商双向互审。
- **兜底策略**: 故障转移（同档换厂商）与质量升级（升档重做）两条轨道及其触发条件、重试预算、熔断窗口。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一基准任务集上，总成本（按各厂商计价合计）较"全程强模型"基线下降 ≥ 40%，且任务交付质量不低于基线（review 通过率与缺陷数不劣化）。
- **SC-002**: 交叉 review 覆盖率 100%：代码 100% 经异源厂商复核、计划/决策 100% 经互审；任何降级（单厂商可用）100% 显式标记，0 次静默跳过。
- **SC-003**: 单一厂商故障场景下 ≥ 90% 的任务无需人工干预自动完成，其中 ≥ 90% 在 2 次重试内恢复。
- **SC-004**: 语义决策服务故障场景下任务不中断率 100%（自动回退默认规则）。
- **SC-005**: 增删厂商/调整模型池配置后即时生效，代码改动量为 0。
- **SC-006**: 非新建会话中主会话模型切换次数为 0；新建会话按轮切换不受限。

## Assumptions

- 运行宿主为 pi（pi-coding-agent），利用其"子代理可指定模型"能力实现派发；宿主不具备大小模型自动路由能力，由本功能补齐。
- 语义决策服务采用 TypeSafe Jev（evaluation 型决策模型，经 Vercel AI Gateway 调用），凭据已配置；决策调用为独立评估请求，不进入任何对话上下文。
- 默认强模型池：mimo/mimo-v2.6-pro、glm/glm-5.3；默认实现模型池：deepseek/deepseek-flash、glm/glm-5.3-flash、relay/cmd-deepseek-v4.1-flash、opencode-go/deepseek-flash（均为当前 pi 已注册供应商，仅为默认值，可配置更换）。
- 中转通道（relay、opencode-go）是否保留厂商侧前缀缓存待实测验证；若不保留，路由权重相应下调——这属于实施期验证项，不影响需求语义。
- 前置缓存保护策略：主会话模型不切换 + 实现走独立上下文执行者（缓存边界与角色边界对齐）+ 会话空闲期缓存保活，三者共同满足 SC-006 的延迟目标。
- 范围外（Non-Goals）：多机分布式调度；pi 之外的宿主（Claude Code / Codex 等）适配；跨厂商 KV 缓存共享（物理上不可行）。
- 二期演进（不在本期验收范围）：路由租约、缓存亲和信号进决策、pi extension 化集成。
- 上下文超长时依赖宿主自动压缩机制，本功能不自行实现压缩。
